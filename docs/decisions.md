# Decisions and deviations from the design

Design v1.0 was recorded before the code and remains as history. This file records the implementation decisions.

- **Modular monolith, two instances:** pure rules in `ledger`, persistence in `postgres`, HTTP and the dispatcher in `httpapi`. There is no Redis, broker, or extra distributed coordinator: PostgreSQL is the concurrency authority.
- **Simplified representation:** a single currency, BRL; positive accounts are clients, -1 through -32 are external controls. Source, destination, and amount live in the operation's canonical JSONB payload. Postings use the sign of the delta and the key `(operation_id, account_id)`; a transfer does not accept a source equal to the destination.
- **Prototype authentication:** one service key identifies an institutional caller authorized to operate every account. It does not implement account-holder authentication, per-account permissions, or multiple tenants. The idempotency key is global in this domain. A public client API would need per-account authorization and binding of identity to the key before production.
- **Immutability:** a trigger rejects UPDATE/DELETE of postings. The local user owns the schema so Compose can run migrations; that does not represent production privilege separation. In production, migrations and runtime need separate roles.
- **Reversals:** internal IDs use `refund:`; `:` is not allowed in client IDs. That prevents the client from occupying a reversal identity in advance. The original operation is locked while its settlement changes; compensation and the terminal state are atomic.
- **External integration:** simulator with a separate database; `reject:` on the recipient produces a definitive rejection. A lost response means repeating the same ID, never reversing because of a timeout. APPROVED is local authorization; PENDING/SETTLED/REVERSED report settlement separately. Recipient idempotency is an assumption of the integration, not a property imposed by the network.
- **Numeric limit:** credit overflow causes a decline. If a reversal credit hit the bigint limit, the transaction would be rolled back and the outflow would stay PENDING for intervention; there is no discard and no negative balance. Commercial limits below bigint are required in production.
- **Infrastructure:** the Go build image is pulled from the public ECR mirror, because of Docker Hub DNS failures in this environment. Runtime uses a scratch image, a numeric unprivileged user, and CA certificates. PostgreSQL 16, with fsync and synchronous_commit left on.
- **Account log, not the row:** authorization orders the balance in the batch and writes only the increment to `entries` and `operations`. The current balance is the `balance_after` of the last posting. The `accounts` row is not rewritten on that path; a reversal aligns the row with the log before posting. One writer at a time remains on the advisory lock. The default window is 15 ms so group commit can join dozens of requests. `fsync` stays on.
- **Quality:** coverage is measured on internal production code, not on CLIs, scripts, or dependencies. Mutation is aimed at the monetary rules, with an explicit scope; it is not a claim of mutation coverage for the whole system.
- **Explicit domain:** monetary rules, identities, and the decision live in `internal/domain`, split by folder: `valueobject`, `aggregate`, `entity`, `errs`, `policy`, `service`, and `repository`. The input and output contract carried by the batch and by HTTP is `internal/application/dto`. The 100% coverage measures everything under `internal/domain`. The nine semantic mutants change `internal/domain/policy/policy.go`. SQL, the batch, and the outbox stay in `postgres`.
- **Application:** use cases and DTOs live in `internal/application` (`dto`, `port`, `usecase`). Application authorization validates the command in the domain, handles replay, conflict, and a missing account, and stores the `service.Authorization` through a port. HTTP and the microbatch stay on the current path until the adapter.
- **Infrastructure:** connection, schema, microbatch, and outbox live in `internal/infrastructure/postgres`, with repositories in `account`, `transfer`, `statement`, `receipt`, and `codec`. `SaveAccount` materializes the row only when the balance and sequence are already the end of the log. `SaveTransfer` writes the operation; an approval without both postings is `ErrInvariant`. `Commit` and `SaveReceipt` re-enter `Authorize` and `Receive`. `POST /transfers` stays on the microbatch. Infrastructure does not import presentation.
- **Presentation:** HTTP lives in `internal/presentation/httpapi`. The input DTO validates the JSON and the request in the domain before the controller. Queries and the simulator call the use cases. `POST /transfers` stays on the microbatch.
- **Microbatch on the authorization path:** the one-transaction-per-transfer baseline sustained about 700 req/s on the hot account and fell to about 19 approvals/s at 2,000 req/s. `POST /transfers` now enters a batch of at most 64 requests. The intermediate balance is validated in order, with `ledger.Decide`, and the commit writes the individual postings and the final balance once. A `pg_advisory_xact_lock` guarantees one batch writing at a time: two executors on the same hot account doubled the row updates, and lock wait pushed out the tail. Inside the batch, accounts stay locked with `SELECT … FOR NO KEY UPDATE ORDER BY id`. A repeated `transaction_id` is isolated with `ON CONFLICT` and a savepoint; it does not undo the rest of the batch. The batch has its own 1.2 s deadline and HTTP waits up to 1.5 s. A 250/300 ms deadline turned the wait for the other instance's lock into a 503, even though the following commit stored the operation. p99 remains the target; the short deadline no longer turns an fsync hiccup into a technical error. A full queue responds immediately with a technical error and the same id. An external reversal stays in the settlement transaction, locking accounts in the same order; the two writers do not update the balance without that lock. Window and size are `BATCH_WINDOW_MS` and `BATCH_SIZE`. In the 20 s comparison at 2,000 req/s, batch 64 with a 2 ms window had p99 of 24 ms and zero errors; batch 64 with 8 ms had p99 of 35 ms; batch 16 with 8 ms had p99 of 37 ms. The window waits only when the queue is empty. With a full queue, the batch drains up to 64 before writing, so a hiccup does not leave the account permanently behind arrival. The default remains batch 64 and a 2 ms window. Compose Postgres uses `shared_buffers` of 512 MB, `max_wal_size` of 4 GB, and a 15 min checkpoint. `fsync` and `synchronous_commit` stay on.

## TigerBeetle replaces PostgreSQL (branch `tigerbeetle`, 2026-10-01)

The bullets above describe the PostgreSQL implementation and stay as history. Where they conflict with this section, this section wins.

- **Single financial authority:** TigerBeetle 0.17.9 (`ghcr.io/tigerbeetle/tigerbeetle:0.17.9`, Go client `tigerbeetle-go` v0.17.9) holds accounts, transfers, balances, history, idempotency and the external settlement state. PostgreSQL, pgx, the schema, the outbox table and the advisory lock are removed. One replica, cluster 0, data on the `tbdata` volume; the image's io_uring needs `seccomp=unconfined`, and so does the API, because the client links the same IO layer.
- **No app batcher, queue or lock for correctness:** TigerBeetle checks `debits_must_not_exceed_credits` and the transfer id in the same commit, so authorization is one `create_transfers` with no read first. Each event in a request succeeds or fails on its own; only `linked` chains are atomic. The old batcher's savepoints, retries and writer lock have no counterpart.
- **A 5 ms coalescing window remains, for throughput only:** the client batches only what queues while its single request is in flight. At sub-millisecond latency that is about one transfer per request, and per-request cost dominated. Measured with a probe at 2,000 transfers/s over 1M seeded accounts: no window gave p99 130 ms and max 690 ms; a 5 ms window gave p99 51 ms and max 235 ms. `create` joins concurrent calls for `TB_BATCH_WINDOW` (default 5 ms, 0 disables, max 50 ms) and splits the results by offset. Because events are independent, the window changes no decision. A caller whose context ends while waiting gets "outcome unknown"; the batch may still commit.
- **Grid cache 2 GiB:** with 512 MiB, writes spread over 1M accounts stalled the loop up to 1.7 s; 2 GiB brought the probe's p99 from 1.1 s to 76 ms. TigerBeetle uses about 4 GiB of the 7.6 GiB Docker VM. The test cluster (`tigerbeetle-test`, `--development`, about 1.4 GiB) runs only under the `test` profile.
- **`transaction_id` is an RFC 4122 UUID (contract change):** it is the 128-bit transfer id, so a statement can show the client's id. Ids are lowercased. Only variant `10xx` with versions 1–8 is accepted. The ledger derives its own ids (`sha256(tag‖id)[:16]` with variant bits `11`) for settlement, decline records, memos, receipts, seed funding and mint, so a client cannot occupy them. `refund:<uuid>` remains only as the statement label of a void.
- **Accounts:** ledger 1 (BRL). Client `n` is `u128(0,n)` with `debits_must_not_exceed_credits | history`. Technical shard `-k` is `u128(1,k)`, guarded. Treasury `u128(2,1)` is guarded; mint `u128(2,2)` has no limit; memo accounts `u128(2,3)`/`u128(2,4)` carry zero-amount records. The simulator uses ledger 2 (`u128(3,1)` → `u128(3,2)`). Bootstrap mints exactly `MaxInt64` from mint to treasury once, so the money outside the mint is fixed. Every balance therefore fits in int64, and the old overflow decline cannot happen.
- **Available balance:** `credits_posted − debits_posted − debits_pending` (`policy.Available`). A reserved external send is not spendable; pending credits are not spendable yet.
- **Decisions:** `created`/`exists` → APPROVED; `exceeds_credits` → DECLINED `INSUFFICIENT_FUNDS`; `debit_`/`credit_account_not_found` → DECLINED `ACCOUNT_NOT_FOUND` (new reason value). `exists_with_different_*` → 409 conflict. Any other status is `ErrInvariant`, which maps to 503.
- **Replay and conflict:** for an internal transfer, TigerBeetle compares debit account, credit account and amount on a replay, so a different payload is a conflict without app data. `user_data_128` stays zero there, which also saves an index insert of a random key. An external send stores `Fingerprint()` in `user_data_128` because the reference lives in memos.
- **Declines are recorded:** a refused id becomes `id_already_failed`. The adapter writes a zero-amount decline record (`derive("decline", T)`, code 4) with the fingerprint and a reason code. A replay returns the stored reason, or a conflict if the fingerprint differs. If the process died between the refusal and the record, the replay decides the reason again from account existence. Known limit: if the missing account was created in between, the replay answers `INSUFFICIENT_FUNDS`.
- **External send:** one linked chain holds a pending transfer from the client to its technical shard (code 2, `user_data_32` = reference length) plus up to five zero-amount memos. Each memo carries 28 bytes of the reference in its user data. The reservation and its reference commit atomically. Settlement is a post (`AmountMax`, SETTLED) or a void (REVERSED) under `derive("settle", T)`. TigerBeetle resolves a pending transfer at most once: a repeated rejection returns `exists`, and the opposite decision returns `exists_with_different_flags` (an invariant error). A refund is only ever the void, atomic with the final state.
- **Outbox replaced by a scan:** the worker queries ledger 1 code 2 in commit order. It keeps reservations with no settlement record, reads their memos, delivers to the simulator and settles. Each sweep runs to the end, then the next sweep restarts at the oldest still-open reservation, so one failing delivery does not hide later ones. A restart sweeps from the beginning. Both API instances run the worker; duplicates are harmless because the receipt and the settlement are idempotent.
- **Statement and sequence:** clients have `history`. A page zips `get_account_transfers` with `get_account_balances` (same timestamps). The sequence is TigerBeetle's commit timestamp, the delta comes from `policy.Delta`, and `balance_after` is the available balance of that snapshot. Funding and capture rows (zero client delta) are skipped but advance `next_after`. A void appears as `refund:<uuid>` with a positive delta. The balance endpoint's sequence is the newest snapshot's timestamp; the first statement request pins it as `until`.
- **Seed:** creates the accounts and one funding transfer each (`derive("seed", account)`, code 3) from the treasury. A second seed keeps existing balances. The chunk starts at 8,189 events and halves on `ErrTooMuchData`, because the development cluster accepts about 250 per request.
- **Timeouts:** client calls cannot be cancelled and retry forever. Every call runs in a goroutine bounded by the request context; on expiry the API answers 503 `OUTCOME_UNKNOWN_RETRY_SAME_ID`, never a decline. Readiness reads the treasury, because a recovering replica already accepts connections and `Nop` succeeded before it could commit.
- **Audit:** TigerBeetle has no read snapshot, so `make audit` runs with traffic stopped. It checks: every non-mint account has a non-negative int64 available balance; the money outside the mint equals `MaxInt64` and pending debits equal pending credits; and for chosen accounts every history prefix is valid and the newest snapshot equals the account. It also counts unresolved external reservations. Two postings per approval and zero per decline are TigerBeetle's double-entry structure, not recomputed.
- **Tests:** integration, HTTP and acceptance tests use the development cluster at `TEST_TB_ADDRESS` (`make test-ledger`). TigerBeetle cannot truncate, so each test uses a random account range and random UUIDs. CI starts the cluster with `make test-ledger`, because a services container cannot take the custom entrypoint and seccomp option.
- **Build:** cgo is required. The image links statically against musl (`-linkmode external -extldflags -static`) and keeps a `scratch` runtime. On macOS the new Apple linker rejects the client archive, so the Makefile sets `CGO_LDFLAGS=-Wl,-ld_classic` on Darwin.
- **Load measurement placement:** the passing 10-minute run used k6 inside the Compose network (`grafana/k6`, `api:8080`, `api2:8080`). The same load from the macOS host, through Docker Desktop's port forwarder, had p99 148 ms and 0 dropped iterations, but 4 of 1.2M requests ended in `EOF` on a reused connection. A host run at 2,000 POST/s that never reaches the ledger had zero such errors, and no panic or server error was logged. The root cause of those 4 was not isolated. Both results are in `reports/`.
